# 좌표 라벨 만들기 — 실버 + LLM 라벨 + 사람 감사 (2026-07-31)

## 라벨 주체를 어떻게 정했나

처음에는 "LLM이 라벨하면 순환 논증"이라고 봤으나, 그 판단은 과했다.
**파이프라인은 LLM의 in-context 추론이 아니라 이미 고정된 규칙 코드**
(키워드 스코어링, 단위 차원 규칙, API 검증)라서 라벨링과는 다른 프로세스다.

다만 남는 진짜 위험은 **상관된 오류**다. `item_mapping_type` / `choose_item` 의
매칭 휴리스틱에는 "이런 주장은 이런 ITEM에 붙는다"는 같은 믿음이 들어가 있다.
그 믿음이 틀린 지점에서는 라벨과 파이프라인이 **같이** 틀리고, 평가는 정답이라 말한다.

그래서 라벨을 금지하는 대신 **오류가 검출되게** 설계했다.

| 단계 | 주체 | 산출물 |
|---|---|---|
| 1. 값으로 확정되는 것 | 기계 (KOSIS 실제값 대조) | `silver_coordinates.csv` |
| 2. 나머지 판단 | LLM (증거 시트 기반) | `labeling_packet.csv` |
| 3. 층화 표본 30건 감사 | 사람 | 라벨 오류율 |
| 4. 보고 | — | 지표 + **출처·감사 결과 병기** |

3단계가 핵심이다. 30건 감사로 라벨이 "검증 안 된 것"에서 **"오차가 측정된 것"**
으로 바뀐다. 177건 전수 라벨보다 훨씬 싸다.

보고 형식은 항상 이렇게 쓴다:
`recall@5 = 0.70 (LLM 라벨, 사람 감사 n=30, 일치율 X%)`

`labeling_packet.csv` 의 `pipeline_choice` 컬럼은 라벨과 파이프라인이 일치하는
행을 식별하기 위한 것이다. **그 행들이 상관 오류 위험이 높으므로 감사 표본에서
과대추출**한다.

## 1단계: 실버 — KOSIS 실제값 대조

## 실버(silver) 좌표란

`build_silver_coordinates.py` 가 measurement 마다 A/C 양쪽 후보 좌표를 모아
중복 제거하고, **좌표를 고정한 채**(`verify_row(use_pinned_item=True)`)
KOSIS 실제값을 조회해 기사 값과 비교한다. 기사 숫자를 재현하는 좌표만 후보로 본다.

| tier | 조건 | 처리 |
|---|---|---|
| `SILVER_UNIQUE` | 정확히 한 좌표만 값을 재현 | 검색 평가에 사용 |
| `SILVER_AMBIGUOUS` | 두 개 이상이 재현 | 기계가 못 고름 → 사람 |
| `NEAR_MISS` | 오차밴드(`판정보류`)만 존재 | 사람 |
| `NO_MATCH` | 재현 좌표 없음 | 라벨 불가 |

`verify_row` 는 원래 `choose_item` 으로 ITEM 을 **다시 고른다**. 그러면
"A 후보 좌표 vs C 후보 좌표" 비교가 성립하지 않으므로 `pin_item` 경로를 추가했다
(opt-in, 기존 동작 불변).

## 이 라벨의 구조적 한계

1. **참인 주장 쪽으로 편향된다.** 기사 숫자가 틀린 주장 — 즉 우리가 잡아내야 할
   대상 — 에서는 어떤 좌표도 값을 재현하지 못해 라벨이 생기지 않는다.
2. **판정(verdict) 정확도 측정에 쓰면 순환 논증이다.** "기사가 맞다"고 가정해
   좌표를 정한 뒤 그 좌표로 기사를 채점하게 된다.
3. 쓸 수 있는 용도는 **검색 비교 하나뿐**이고, 그것도 편향된 부분집합 위에서의
   비교임을 분모와 함께 항상 명시해야 한다.

**실버는 A팀 골드를 대체하지 않는다.** 골드가 오면 실버와 대조해 실버 적중률부터 보고한다.

## 2단계: LLM 라벨 (증거 기반)

`export_labeling_packet.py` 가 실버가 못 푼 measurement 만 모아 근거 시트를 만든다.
라벨러가 prior 가 아니라 증거를 보게 하는 것이 설계 목표다.

- 후보 좌표마다 **KOSIS 메타 이름·단위 + 실제 조회값 + 판정**을 붙인다.
- 후보는 **파이프라인 순위가 아니라 코드 사전순**으로 낸다(1위 앵커링 방지).
- 라벨러는 행마다 `label_evidence`(근거)와 `label_confidence`를 반드시 적는다.
- 맞는 좌표가 없으면 `없음`, 판단이 안 서면 `보류`.

## 3단계: 사람 감사 (필수)

층화 표본 30건. 아래 비율로 뽑는다.

| 층 | 비중 | 이유 |
|---|---|---|
| 라벨 == `pipeline_choice` | 15건 | **상관 오류 위험이 가장 높은 구간** |
| 라벨 != `pipeline_choice` | 10건 | 라벨이 파이프라인을 뒤집은 근거 확인 |
| `SILVER_UNIQUE` 표본 | 5건 | 실버 자체의 신뢰도 |

감사 결과로 라벨 오류율을 산출하고, 이후 모든 지표에 병기한다.

## A팀 골드가 오면

실버·LLM 라벨을 **대체**하고, 먼저 **실버/LLM 라벨이 얼마나 맞았는지 대조 보고**한다.
`gold_tbl_id` / `gold_itm_id` / `gold_obj_l1` 컬럼은 **비워 둔 채로** 나간다.
실버 값으로 미리 채우면 라벨러가 그대로 끌려간다(앵커링).

| 컬럼 | 내용 |
|---|---|
| `gold_tbl_id` | 정답 통계표 ID. KOSIS에 해당 통계가 없으면 `없음` |
| `gold_itm_id` | 정답 ITEM 코드 |
| `gold_obj_l1` | 정답 분류축 코드 |
| `gold_confirmed_by` | 라벨러 |
| `gold_note` | 애매했던 이유 |

### 우선순위

라벨 비용을 줄이려면 아래 순서로 준다.

1. `SILVER_AMBIGUOUS` / `NEAR_MISS` — **여기가 제일 값어치 있다.**
   기계가 못 고른 지점이고, `needs_human_review.csv` 에 후보가 정리돼 있어
   "고르기"만 하면 된다.
2. `NO_MATCH` — 기사가 틀린 것인지 좌표를 못 찾은 것인지 갈린다. 판정 골드의 씨앗.
3. `SILVER_UNIQUE` 중 표본 20건 — 실버 자체의 신뢰도 검수용.

### 왜 필요한지 (실측 근거)

1차 Colab 실행에서 A와 C 둘 다 API 검증을 통과한 **85 measurement 중 좌표가
일치하는 것은 31건뿐**이었다. 나머지 54건은 서로 다른 좌표인데 양쪽 다 KOSIS가
값을 돌려줬다. `response_code_valid` 는 코드 일치만 보증하고 값의 정당성은
보증하지 않는다. **어느 쪽이 맞는지는 사람 라벨 없이는 판정 불가다.**

## 실행

```bash
# 1) 실버 생성 (KOSIS API 조회, measurement 당 최대 12좌표)
python build_silver_coordinates.py \
  --measurements 05_hcx_measurements_kosis_ready.csv \
  --candidates-a 05_hcx_measurements_kosis_validated_mappings.csv \
  --candidates-c chroma_hybrid/05_hcx_measurements_kosis_chroma_validated.csv \
  --output silver_coordinates.csv \
  --review-output needs_human_review.csv

# 2) 실버 위에서 A vs C 검색 재비교
#    (노트북 셀 15가 silver_as_gold.csv 를 만들어 evaluate 에 넘긴다)
```

Colab: 노트북 셀 14 → 15. 예상 호출 수는 최대 177 × 12 ≈ 2,100회.

테스트: `tests/test_build_silver_coordinates.py` (좌표 고정, 중복 제거, tier 판정, probe 구성).
